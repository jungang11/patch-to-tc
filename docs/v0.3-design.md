# v0.3 Design Notes

This file is a working design document for the three candidates the project is considering for v0.3. It captures problem statements, options, trade-offs, and a current recommendation per item — **without committing to implementation**.

Implementation begins only after a separate review approves the recommendation in a later session.

Last updated: 2026-05-18.

| Item | Status | Current recommendation | Target version |

| Project-format branching | designed, deferred | Option B (separate skill per domain) — defer until non-mobile demand emerges | v0.4 |

## 1. xlsx / csv output

### Problem

Downstream users often manage QA in xlsx (corporate) or csv (CI-friendly). The skill currently emits Markdown only, so users hand-copy or grep into other tools. Adding `xlsx`/`csv` output would shorten the path from skill invocation to QA tool.

### Options

#### Option A — SKILL.md Stage 5 emits CSV/XLSX directly

Add a fourth Notion-mode-like argument: `--format markdown|csv`. xlsx is excluded because LLMs cannot produce binary reliably.

**Pros**
- Single interface in the skill.
- No external dependency for users.

**Cons**
- CSV escaping (commas in steps, newlines in expected results) is fragile when an LLM generates row-by-row.
- Stage 5 grows; SKILL.md approaches the 500-line ceiling.
- xlsx is still impossible without an external converter.

#### Option B — External converter script

Skill produces Markdown only. `scripts/md_to_csv.py` (and optionally `md_to_xlsx.py`) parses the Markdown table and emits CSV/xlsx deterministically.

**Pros**
- Skill stays simple; SKILL.md unchanged.
- CSV/xlsx conversion is deterministic — no LLM involvement, no escaping surprises.
- Python `pandas` / `openpyxl` are mature.

**Cons**
- Python dependency for downstream users.
- Two-step flow: invoke skill → run converter.

#### Option C — Rely on Notion DB write

The skill already supports `notion-draft` / `notion-write`. Users export from the Notion DB to xlsx/csv via Notion UI.

**Pros**
- Zero new code.
- Schema-confirmation protocol already handles property mismatch safely.

**Cons**
- Requires Notion. Many downstream environments do not use Notion.
- Notion → xlsx export is a manual user step.

### Recommendation

**Option B**, but **defer to v0.4** until real downstream demand is confirmed. The downstream-adoption trial (separate task) will reveal whether Markdown is actually a friction point or whether teams are happy to paste into their own tooling.

When implementing: start with `scripts/md_to_csv.py` only. xlsx can be a wrapper over CSV via `pandas.to_excel`.

### Rejected: Option A

CSV escaping in LLM output is the dominant failure mode here. Determinism wins.

## 2. Project-format branching (mobile vs non-mobile)

### Problem

Current `mobile-build-tc-from-diff` is mobile/Unity-domain. The taxonomy (`manifest-change`, `lifecycle`, `addressables-cache`, `permission-flow`, etc.) does not map cleanly to web SPA, backend services, or desktop. Applying it to non-mobile diffs would produce awkward categorizations.

### Options

#### Option A — Single skill with `--domain` argument

`/mobile-build-tc-from-diff android HEAD~3..HEAD --domain web` would load a different taxonomy per domain.

**Pros**
- Single entry point.

**Cons**
- SKILL.md grows to reference all domains' taxonomies — likely exceeds the 500-line ceiling.
- The frontmatter `description` (used for trigger routing) becomes contradictory: "for mobile builds, also for web builds…" reduces trigger precision.
- Cross-domain context bleed risk.

#### Option B — Separate skill per domain

- `mobile-build-tc-from-diff` (current)
- `web-build-tc-from-diff` (future)
- `server-build-tc-from-diff` (future)

Each has its own SKILL.md + taxonomy. Common `references/` (notion-context-policy, notion-output-schema, pairwise-strategy) can be shared by reference or copied per skill.

**Pros**
- Each SKILL.md stays compact (<500 lines).
- Trigger description per skill is precise.
- Failure in one domain doesn't pollute others.

**Cons**
- Skill count grows (3-4).
- Shared references need a sync strategy (symlink within the repo, or copy-and-track).

#### Option C — Base skill + specialization

`build-tc-from-diff` (base, dispatches by detected file types) + `mobile-build-tc-from-diff` (specialization that actually runs).

**Pros**
- Clean abstraction in principle.

**Cons**
- Claude Code does not have an explicit "base + specialization" pattern documented. Building it on top of regular skills produces routing ambiguity (which skill triggers first?).
- User confusion: which skill to invoke?

### Recommendation

**Option B**, **defer to v0.4** or later. Wait until at least one concrete non-mobile project asks for this. Building `web-build-tc-from-diff` speculatively risks designing for the wrong shape — without a real diff to test against, the taxonomy will be wrong.

### Rejected: Option C

Until Claude Code documents a base-specialization pattern, building one on regular skills introduces routing failure modes that outweigh the abstraction benefit.

## 3. Self-update mechanism

### Problem

After installing the skill via bootstrap, downstream users don't know when a new patch-to-tc version is available. They must remember to `git pull` patch-to-tc periodically and re-run bootstrap.

### Options

#### Option A — Manual `git pull` + bootstrap re-run (current state)

User periodically:
```
cd patch-to-tc
git pull
.\bootstrap.ps1 -TargetProject <project>
```

**Pros**
- Zero new code.
- Zero new permissions.
- Predictable: user is in control of when updates happen.

**Cons**
- User may not know a new version exists.

#### Option B — Skill checks remote on every invocation

Stage 0 adds a step: fetch the remote SKILL.md (or a `version` file) from `https://raw.githubusercontent.com/jungang11/patch-to-tc/main/...` and compare against local. On mismatch, print "v0.3.0 available, run `git pull` + bootstrap to update".

**Required frontmatter additions**
- `WebFetch(https://raw.githubusercontent.com/jungang11/patch-to-tc/*)` — narrow URL allowlist
- OR `Bash(curl -s https://raw.githubusercontent.com/jungang11/patch-to-tc/*)` — same scope

**Pros**
- User learns about new versions automatically.
- Read-only — no automatic modification of files.

**Cons**
- Adds an external-fetch permission to `allowed-tools`. The security audit explicitly flagged that frontmatter is pre-approval, not sandbox — adding any new external endpoint enlarges the trust surface even if the call site is benign.
- Every invocation pays a network round-trip (~hundreds of ms).
- Offline / restricted-network environments see a failure or noisy warning on every invocation.

#### Option C — Option B + 24h cache

`.cache/patch-to-tc/last-check` stores the last fetch timestamp. Skip the remote fetch if checked within 24h.

**Pros**
- Network cost reduced 95%+.

**Cons**
- Adds local file write (cache management).
- Stale-cache scenarios: user just `git pull`ed manually 5 minutes ago; cache still says "old version". Minor.

#### Option D — Downstream CI / GitHub Action

Downstream project owner sets up a daily GitHub Action that diffs their `.claude/skills/mobile-build-tc-from-diff/` against the upstream patch-to-tc and opens a PR / issue.

**Pros**
- Skill itself is unchanged.
- No new permission.

**Cons**
- The downstream team has to set this up themselves.
- patch-to-tc cannot enforce it.

### Recommendation

**Option A (no change)** + add **a one-line note in README**: "Re-run bootstrap occasionally (or set up a calendar reminder) — patch-to-tc updates do not auto-propagate."

Option B/C add an external-fetch permission for the sake of a "version available" toast. The benefit-cost ratio is poor: the security audit just spent effort tightening `allowed-tools`; widening it for a UX nicety is a regression in the security posture.

Option D is a downstream-side concern outside this repo's scope.

### Rejected: Option B and C

External-fetch permission is a meaningful security cost. The friction it removes is small (users currently know about the project; missing a version by a few weeks is rarely critical).

## Reassessment triggers

This design becomes stale (and should be re-discussed) when any of:

- A downstream user reports a concrete CSV/xlsx need with a workflow example.
- Someone wants to apply the skill to a non-mobile project.
- A real security-audit finding requires self-update notification (e.g., known vulnerability patched in v0.x, users must update urgently).
- Claude Code introduces an explicit base-skill / specialization pattern.

Until then, the current `mobile-build-tc-from-diff` skill + manual update flow is the intentional shape.
